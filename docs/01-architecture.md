# 01 · 生命周期架构设计

## 1. 设计出发点

企业在推进 AI 落地时普遍遇到四个问题：

| 问题 | 表现 | 平台对策 |
| --- | --- | --- |
| AI 需求分散 | 需求散落在各部门聊天记录、会议纪要里，没有统一入口 | 「场景发现 / 需求分析」模块收口需求 |
| 场景价值难判断 | 谁都说自己的场景重要，缺乏统一评估维度 | 需求分析阶段输出结构化价值/可行性判断 |
| 知识资产难复用 | 做过的方案、踩过的坑无人沉淀 | RAG 四类知识库 + 反馈回流 |
| 应用效果缺乏统一评估 | 上线即结束，没人回头看有没有用 | 「效果评估」模块 + 四维评测框架 |

平台服务三类角色：

- **业务角色**：提交需求、使用生成的成果、给反馈
- **应用建设角色**：设计/调试 AI 应用与知识库
- **运营管理角色**：看全局数据、管权限、管版本、评估效果

## 2. 六大模块与数据流转

```
┌───────────┐   需求线索    ┌───────────┐  结构化需求  ┌───────────┐
│ 场景发现   │ ───────────> │ 需求分析   │ ──────────> │ 方案设计   │
└───────────┘              └───────────┘             └─────┬─────┘
                                                          │ 应用方案 + 资源规划
                                                    ⛳ 人工审核卡点 1
                                                          ▼
┌───────────┐   复用记录    ┌───────────┐  结构化成果  ┌───────────┐
│ 推广复用   │ <─────────── │ 应用建设   │ <────────── │  (方案已确认) │
└─────┬─────┘              └───────────┘             └───────────┘
      │ 复用数据
      ▼
┌───────────┐
│ 效果评估   │ ──> 四维评测结果 ──⛳ 人工审核卡点 2（成果输出）──> 正式成果
└─────┬─────┘
      │ 用户修改 / 评估结论
      └──────────────> 反馈回流：沉淀回 RAG 知识库
```

### 各模块输入 / 输出契约

| 模块 | 输入 | 输出 | 是否自动 |
| --- | --- | --- | --- |
| 场景发现 | 需求线索（自然语言） | 候选场景清单 | 全自动 |
| 需求分析 | 候选场景 + 背景信息 | 结构化需求（目标 / 约束 / 价值判断 / 待确认项） | 全自动 |
| 方案设计 | 结构化需求 + 知识库检索结果 | 应用方案 + 资源规划 | 全自动生成，**人工确认后放行** |
| 应用建设 | 已确认方案 | 结构化成果（文档 / 清单 / 配置） | 全自动 |
| 推广复用 | 结构化成果 + 使用数据 | 复用记录 + 可复用模板入库 | 全自动 |
| 效果评估 | 使用数据 + 反馈数据 | 四维评测结论 + 改进项 | 全自动分析，**报告输出人工确认** |

### 为什么只在两处设卡点

- **方案设计**：方案错了，后面全错，且方案涉及资源投入判断，必须人来担责。
- **成果输出**：对外正式产物，AI 幻觉在这里代价最高。

其余环节（场景发现、需求分析、应用建设、推广复用、效果分析）都是"可回退、低对外风险"，全自动执行以保证吞吐。

## 3. 原型场景映射（活动运营 SOP）

本仓库把抽象的六大模块实例化为「活动运营」场景。前端 `index.html` 呈现为 5 个阶段：

| 前端阶段 | 生命周期模块 | Dify 应用 | 人工卡点 |
| --- | --- | --- | --- |
| 01 · 策划（SOP 大纲） | 场景发现 + 需求分析 + 方案设计 | A1 | 确认大纲 |
| 02 · 执行（执行主表） | 方案设计 | A2 | ⛳ 确认主表（负责人/日期/预算） |
| 03 · 成果（配套成果） | 应用建设 | A3 | — |
| 04 · 复盘（复盘分析） | 效果评估 | R1 | 确认结论口径 |
| 05 · 沉淀（复盘报告） | 效果评估 + 推广复用 | R2 | ⛳ 确认报告 |

横切能力 **A4 AI 修改助手**（Chatflow）贯穿 01–05：任何阶段都能对话式调整，
修改只生成新草稿（`versions` 字段），人工确认后才发布为正式版，正式版永不被直接覆盖。

数据落地在 `projects` 表：`a1_data ~ r2_data` 六个 JSON 列存各阶段产物，`versions` 存版本历史，`feed` 存操作时间线。

## 4. 关键设计取舍

| 决策 | 取舍 |
| --- | --- |
| 六模块用**数据契约**而非流程引擎串联 | 每个模块可独立替换/复用到别的场景，代价是流转逻辑分散在前端 + Dify |
| AI 编排放 Dify，不放后端 | 产品经理/运营可自行改 Prompt 与分支，后端零改动；代价是链路可观测性依赖 Dify + 自建 `dify_calls` 留痕 |
| "待确认"而非阻断 | 信息不全也能先生成，缺口显式标注，不打断用户心流 |
| 单文件前端 | 演示零构建、易分发；不适合继续长大 |
