# 04 · 质量评估机制设计

## 1. 四维评测框架

每条测试 Case 从四个维度打分（人工 Grader 结合规则校验）：

| 维度 | 问的问题 | 规则可自动校验部分 | 需人工判断部分 |
| --- | --- | --- | --- |
| **召回准确性** | 该命中的知识有没有召回？Top-K 是否相关？ | 关键文档 ID 是否出现在召回列表 | 召回内容与 query 的实际相关度 |
| **内容完整性** | 关键字段齐不齐？必备环节漏没漏？ | 必填字段非空校验 | "这个活动类型该有的环节"是否遗漏 |
| **结构化输出规范性** | 输出符不符合约定 Schema？前端能不能解析？ | JSON Schema 校验、字段类型校验 | 字段语义是否放对位置 |
| **异常识别能力** | 信息缺失时是标"待确认"还是编造？ | 是否出现未授权的具体数字/结论 | 编造的隐蔽程度 |

## 2. 测试 Case 设计

- **50+ 条 Case**，覆盖 6 个应用
- 分层：
  - 正常路径（信息完整）
  - 缺信息路径（故意留空背景/预算 → 验异常识别）
  - 边界路径（超长背景、非常见活动类型 → 验召回与完整性）
  - 联动路径（A1 输出喂给 A2 → 验上下文传递）
- 每条 Case 固定：`输入` + `期望命中知识` + `期望字段清单` + `不允许出现的内容`

## 3. 回归流程

```
改动（切片/Prompt/编排）
      │
      ▼
跑全量 50+ Case ──> 规则校验（自动）──> 人工 Grader 复核标红项
      │
      ▼
对比上一轮结果 ──> 新增 BadCase? ──> 归因 ──> 修复 ──> 再回归
```

## 4. BadCase 四类归因

每个 BadCase 必须归到且仅归到一类，各有**可复现的定位口径**：

| 归因类型 | 定位口径（怎么确认是这一类） | 典型修复手段 |
| --- | --- | --- |
| **知识检索** | 把召回结果单独拉出来看：期望文档没进 Top-K，或进了但排序太靠后 | 调整切片粒度、补 Metadata、调双路权重 |
| **上下文传递** | 召回对、但某节点的输入里缺了上游关键字段 | 在 Workflow 该节点补上下文注入 |
| **Prompt 约束** | 输入齐全、但模型没按要求做（如没标"待确认"、格式跑偏） | 增加输出 Schema 约束、加 few-shot、加负向指令 |
| **Workflow 逻辑** | 单节点都对、但分支走错 / 该调的应用没调 | 修正编排条件分支、补节点 |

### 定位顺序

先看召回（最外层）→ 再看各节点输入（中层）→ 再看 Prompt（内层）→ 最后看编排。
从外往里排除，避免一上来就改 Prompt 这种"看起来最快其实治标"的动作。

## 5. 三类高频修复的对应关系

| 现象 | 归因 | 修复 |
| --- | --- | --- |
| 该引用的历史案例没用上 | 知识检索 | 案例库切片从"按文档"改"按阶段"，粒度变细 |
| 复盘报告里缺了 R1 的某项结论 | 上下文传递 | R2 节点补 `r1_analysis` 全量注入 |
| 输出偶尔不是合法 JSON / 字段名漂移 | Prompt 约束 | 增加输出 Schema 约束 + 结尾格式校验节点 |

## 6. 反馈回流

评测闭环之外的第二条回路（见 [02 §6](02-rag-design.md#6-反馈回流)）：

```
用户在前端改了 AI 的成果
      │
      ▼
diff 捕获 ──> 归类（补充/纠错/联动）──> 人工审核 ──> 沉淀回知识库
                                              │
                            下一轮同类 query 直接命中，减少同类 BadCase
```

测试—定位—优化—回归是"内部驱动"的改进，反馈回流是"真实使用驱动"的改进，两者互补。

## 7. 现状与缺口

- 评测目前靠人工执行 + 表格记录，未自动化编排（计划接入评测脚本 + CI）
- Grader 评分标准文档化了，但跨人一致性未做 kappa 校验
- 缺信息路径的 Case 占比偏低，异常识别维度样本还需补充
